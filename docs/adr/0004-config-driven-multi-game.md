# 游戏差异收进游戏档案：资源包即游戏，各机构共用代码

- 状态：accepted（2026-08-29）

需求方提出以同一套工具支持原神、崩坏：星穹铁道、绝区零的强化自动化。调研 MaaFramework 的配置加载能力（ProjectInterface V2 协议）：资源包（resource）是框架原生的按项目划分机制——用户在运行器中选择资源包，任务与选项可按资源包过滤显示，pipeline、模板图、OCR 模型以及任意自定义 JSON 都随资源包分发，后加载覆盖先加载；agent 子进程可从 `PI_RESOURCE` 环境变量（PI v2.5.0 约定）获知用户选中的资源包，MFAAvalonia 已实现该注入（经其 AgentHelper.cs 源码证实，桌面端路径生效）。因此决定：各游戏真正不同的部分（属性与部位代号清单、等级上限、词条变动间隔、星级范围、副词条上限、回合机制）收进每游戏一份的**游戏档案**，随资源包分发；条件树求值、字段校验、观测解析、报告与编辑器全部共用代码，游戏数值零硬编码。第一版仅交付原神（三个游戏中只有原神的界面事实经过真机研究），星穹铁道与绝区零为架构预留，各游戏立项时补档案并做真机研究。代价：格式定义从「固化代号枚举」变为「固化档案结构」，决策机构增加档案加载与校验环节，规则文件增加 `game` 标识以防错配运行。

## Considered Options

- 每游戏一套独立项目（复制仓库分游戏维护）—— 拒绝：三游戏的判定模型、字段校验、报告与编辑器完全同构，分叉是纯维护负担。
- 决策机构内置多游戏分支（按游戏名写条件分支）—— 拒绝：每加一个游戏都要改代码发版；数据进档案后，加游戏只需新增档案与资源包。
- 游戏档案 + 资源包即游戏 + 各机构共用代码 —— 采纳。

依据：`external/maaframework-docs` 3.3 ProjectInterfaceV2 协议（资源覆盖、task.resource 过滤、Agent 子进程环境变量）；MFAAvalonia `AgentHelper.cs`（PI_* 注入实现）。设计细节见 spec §4「游戏档案」、§9。
