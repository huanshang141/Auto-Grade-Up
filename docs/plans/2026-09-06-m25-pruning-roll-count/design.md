# M2.5 设计决策

设计定案的完整推证链见同目录 discussion.md 与 ADR-0006 / ADR-0007；本文只记实现层的决策、理由与被拒备选。

## D1 档案上限表的形状与缺表报错

- 选择：档案新增键 `roll_growth_max`，形状 `{"<星级>": {"<属性代号>": <单次成长最大值>}}`（星级键为字符串数字）；`GameProfile` 增加对应字段与 `growth_max(rarity, code)` 访问方法。缺表两层报错：规则校验层，`candidates.rarity` 引用无表星级 → `RuleValidationError`；求值层，实际圣遗物星级无表 → `ProfileError`（`GameProfile` 增加来源路径字段以支撑报错信息）。
- 理由：剪枝推导的唯一数值输入就是这张表；错误配置在校验期拦截符合「缺数据不做消耗性决策」纪律（与档案缺键同一口径）。
- 被拒：分星级「初始值范围表」——待激活行的预览值就是解锁后的确切初始值（游戏预生成，L1 截图证实），直接读取比维护一张估算表更准。
- 被拒：仅求值层报错——错误规则应在校验期拦截，不该等到求值才暴露。

## D2 词条值对象的字段形状

- 选择：`StatValue` 增加 `roll_count: int | None = None`（可空键、`to_dict` 始终写出，null 表示界面不显示该信息；0 表示界面无标记）与 `pending: bool = False`（键可省略，True 才写出）。`from_dict` 接受键缺省与 null；值域校验（次数 0..⌈max_level/interval⌉、pending 与正次数互斥）由 `validate_artifact` 承担。
- 理由：列表页不显示带圈数字（null）与强化页无标记（0）是两种事实，序列化必须可区分；待激活词条绝大多数情况不出现，全量写出是噪音。
- 被拒：`roll_count` 键缺省省略——0 与 null 无法区分。
- 被拒：独立的待激活词条类型——模型分裂后求值与序列化都要双分支。

## D3 可达值推导

- 选择：`evaluate.py` 增加纯函数推导——剩余变动点数 R = ⌈(max_level − 等级) ÷ 间隔⌉；未来必解锁数 U = min(substat_max − 已解锁条数, R)（含待激活转正）；可分配成长次数 budget = R − U。`sub.<代号>` 的求值实际值 = 词条当前值（待激活行即预览值）+ budget × 档案上限；`roll.<代号>` 的求值实际值 = 当前强化次数 + budget。词条完全不存在（4 条已满且无该代号）→ 缺失语义不变。目标词条不可能出现的情形（如 5 星 3 词条 + 待激活非目标词条）自然落入缺失分支。
- 理由：必解锁挤占是游戏机制（副词条未满 4 条时下一变动点必解锁），不扣除会让可达值虚高、剪枝变钝；乐观方向保证不错杀。
- 被拒：两遍求值（先当前值后乐观值）——同一叶子两种 actual，trace 无法独立复核。

## D4 运算符白名单的边界

- 选择：`sub.*` 与 `roll.*` 字段仅接受 `>` `>=` `exists`，其余运算符在校验层拒绝并同步进 JSON Schema 导出（词条分支的 op 枚举收紧）；`main.*`、标量字段、字符串字段维持现状（`main.*` 保持当前值口径与全部数值运算符）。
- 理由：乐观方向只对增长型条件成立，等于/小于在可达值下语义失真；主词条成长是确定性的（无随机分配），当前值口径天然正确，且 Q7 定案范围未含 `main.*`。
- 被拒：`main.*` 一并收紧——语义未定案，主词条成长曲线表也未录入。

## D5 次数规则体系的接口

- 选择：规则文件顶层新增**可选**键 `roll_rule`（条件树，结构校验与 `rule` 一致，叶子字段仅接受 `roll.*` 命名空间）；`version` 保持 1。求值接口 `evaluate(rule, artifact, profile, roll_rule=None)`：None 表示不求值次数体系（列表初扫传 None、强化页判定传入，调用方显式声明——执行机构持有界面知识，与 ADR-0005 一致）；传入时两棵树都求值，`passed` 为两者与合并。`Judgment.trace` 顶层改为 `{"rule": <树>, "roll_rule": <树或 null>}`。
- 理由：次数数据只在强化页可读（带圈数字仅强化页显示），初扫时次数条件无从求值；显式传参避免按「数据可得性」自动跳过造成的静默放行。
- 被拒：求值器内部按 roll_count 是否为 null 自动跳过——识别异常会被吞成放行。
- 被拒：`roll_rule` 开放全部字段——与 `rule` 职责重叠，两套系统的边界模糊。

## D6 双通道数据的解析层交叉

- 选择：识别结果集新增两个区域键——`roll_marks`（模板对比通道：TemplateMatch 节点在标记列窄条 roi 匹配五张模板图，命中框的纵向位置对应词条行、命中模板对应次数）与 `roll_marks_ocr`（放大 OCR 通道：标记列裁剪放大 4 倍后的 OCR 框，Unicode 带圈字符直接映射 1~5）。交叉在 `read_enhance` 内按行对齐完成：两通道都有值且不一致 → 读取失败；恰好一侧有值 → 取该侧 + 警告（单通道降级）；两侧都无 → 0。放大预处理函数在 M2.5 由录制脚本承载并固化进转储，真机接线（CustomRecognition 复刻同一逻辑）属 M3。
- 理由：交叉逻辑是纯函数（两个框列表 → 每行次数），离线转储即可全量断言；节点内合并（MaaFw 流水线）无法离线测试。
- 被拒：放大 OCR 单通道——真机识别率未经验证，无兜底（ADR-0007）。
- 被拒：TemplateMatch 单通道——弃用 OCR 通道的词条行文本信息。

## D7 防御层语义

- 选择：OCR 通道出现行首孤立短数字（1 倍整图的带圈数字误读形态，如 ①→0、③→3）时，剥离该数字、`roll_count` 记 None（未知）+ 警告入报告；None 在求值时落入缺失语义（数值比较不通过，安全方向）。放大通道下该形态应消失，保留为防御。
- 理由：把误读数字当真值（0→无标记、3→三次）会直接判错次数条件；记未知并放行其余字段比静默判 0 安全。
- 被拒：按读取失败处理——真机高频误读会让系统频繁停机，双通道与警告已提供兜底。

## D8 契约工作副本与折叠

- 选择：四个契约的工作副本在计划期写好（`specs/<capability>/spec.md`，目标态全文），执行收尾任务将全文覆盖正本（`docs/specs/` 四文件），主设计文档 §3/§4/§6/§14 同任务修订。
- 理由：契约与实现同步落定，避免执行期间正本处于新旧混合口径；工作副本全文覆盖消除手工合并错漏。
- 被拒：执行首个任务先改正本——实现尚未落地，正本会描述不存在的行为。
